# Closed Sales deals → Jira clients

Owner controls this automation from Sales or Clients → Client onboarding automation → Configure. Rules live in Supabase, not source code: source tab, company/status columns, exact won value, Jira work project, actual issue type and onboarding title template. OCT and SEP are the currently approved work projects; SOURCE remains separate reference material.

Initial deployment uses Tracksheet → Status = Deal Closed → OCT / actual Task issue type. The actual project create metadata is checked, including required fields and Labels. The first setup excludes existing closed rows to avoid creating tasks for historical deals. Future newly closed deals, including new rows already marked closed, are candidates.

The company name becomes a case-preserving Jira label with whitespace replaced by underscores. Normalized company identities deduplicate repeated lead records. Label collisions between different identities stop processing for Owner review. Existing labelled Jira work in OCT/SEP is linked; otherwise one onboarding issue is created with the label and an issue property holding the conversion reference. No contact, financial, employee login or attendance data is copied into the new issue. No work timer starts. The created task is initially unassigned and uses Jira's default workflow status. Owner assigns work using the existing Jira workflow.

The CRM imports Jira-confirmed work and its label, so the existing Clients and Work views remain based on authoritative Jira data. Subsequent task/status changes use the established Jira sync. A lead is not converted into a standalone manual client profile. Existing conversions are not automatically deleted or renamed if Sales details change; such changes require review rather than silently renaming all Jira labels.

Supabase stores configuration, source baselines and conversion jobs. Employees cannot read or alter this queue/configuration or gain direct Jira creation permission. The server acts under the still-active Owner who enabled the rule. Deactivation/removal of that Owner prevents new job reservations. No secret is stored in the new tables. Service-only database claims prevent overlapping scans and repeated creation attempts across server instances.

The queue is pending → creating → synced, with failed/review states for problems. Confirmed Jira rejection may be explicitly retried by Owner. A timeout, interrupted server or unknown creation outcome is never automatically retried. The known Jira key is stored before importing CRM data. Owner can verify/link an existing Jira key with the expected client label to resolve uncertainty. Jira and Supabase cannot form one atomic transaction; this review path handles that limitation without blindly creating duplicates. Audit records identify the authorizing Owner.

The persistent Node preview/server checks enabled organizations every 30 seconds even when no Sales page is open. The server must stay running. An interval inside serverless hosting is not a durable scheduler; such hosting needs an external server scheduler before unattended operation can be promised. There is no new paid service and no Codex reminder/heartbeat automation.
